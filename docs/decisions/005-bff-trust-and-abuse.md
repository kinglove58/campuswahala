# ADR 005: Signed BFF context and independent abuse dimensions

Status: Accepted for Phase 0.5; deployment integration remains gated.

Browser -> Front Door Premium/WAF -> private authenticated ingress bridge -> game BFF -> internal API. Front Door does not generate our HMAC envelopes. A future private ingress adapter must verify its exclusive Front Door path, strip incoming `X-CW-*` and forwarded client headers, derive the actual client IP from the configured trusted gateway contract, and sign `X-CW-Edge-Context`. No such Azure bridge is deployed or claimed implemented here. The BFF refuses nonlocal requests without a valid bridge assertion. Do not replace this with blindly trusting X-Forwarded-For or a browser fingerprint.

The implemented envelope covers method, exact route, SHA-256 body digest, timestamp, nonce, client identifier and network context. The API envelope additionally binds the guest capability through the signed input digest. HMAC-SHA256 uses independent externally provisioned keys of at least 32 characters: EDGE_SERVICE_SECRET (bridge/BFF), BFF_SERVICE_SECRET (BFF/API), NETWORK_HMAC_SECRET (BFF only; optional local direct-API fallback). SESSION_SECRET remains independent at-rest capability hashing. Local-only shared development key is explicitly named and rejected as an implicit nonlocal fallback. Nonlocal API routes except exact GET health probes require service proof and emit no browser CORS allowance. Health probes carry no session data. Mutations still require exact game Origin; CORS is never authentication.

BFF creates a random signed HttpOnly SameSite=Strict `cw_client` cookie retained 24h. It ignores browser client/context/forwarded headers and overwrites service context. Creation has independent 10/client/minute and 100/pseudonymous-network/minute buckets; guest routes have 60/client/minute and valid guest self/revocation requests additionally 60/capability/minute, catalogue 120/client/minute. These are initial tuning values, not load-tested production quotas. Signed clients behind a BFF do not share a creation bucket. Clearing cookies can evade a client quota but remains subject to network quotas and future edge challenge/bot controls. Many legitimate users may share NAT, so network limits are deliberately broader and must be tuned with false-positive evidence.

Network context is a keyed HMAC of the trusted IP with UTC date/domain separation. Raw IP is transient at ingress/BFF and is never logged or stored in application tables. Identifiers rotate daily; rate counters expire after one minute and replay entries after one minute. No analytics use or permanent pseudonymous IP history. Rotate underlying network key at least quarterly and on compromise through Key Vault. Gateway must canonicalize IPs and apply IPv6/subnet/bot policy before signing; HMAC alone does not defeat IPv6 address rotation. Midnight/key rotation can reset abuse buckets; edge quotas remain independent. Anonymous cookie is not identity or authorization.

Proof validity is strictly less than 30 seconds of clock difference (exclusive endpoints prevent nonce-retention boundary replay); transient replay guards reject reused nonces (10,000-entry bound, fail closed). TLS and private service ingress remain mandatory: signing does not encrypt or prevent origin exposure. Shared atomic replay and rate-limit storage are required before public staging/multiple replicas, with fail-closed outage policy for creation and sensitive routes. Current in-process counters are development evidence only, never a distributed production claim. Key rotation uses a coordinated short drain/rollout; no indefinite previous-key fallback. Future managed-identity authentication can replace HMAC behind this boundary via a new ADR. Account abuse must key on server-verified subject/account, with route/session/network dimensions in addition; never browser-supplied account IDs.

Executable evidence: hardening/API tests reject signatures with changed route/body/key/time, forged headers and replay, enforce nonlocal authentication, and distinguish two signed clients on the same transport/network; Playwright exercises actual BFF cookie/header handling.

Protocol v1: `base64url(JSON payload).hex(HMAC-SHA256(payload))`; payload carries version=1, client, network, method, path, body (SHA-256 hex), at (epoch milliseconds) and nonce (random UUID). The future bridge calls signContext with a canonical IP in network, a server-owned opaque client identifier and raw UTF-8 body for the exact /api/guest path. BFF validates that proof and replaces network with a 64-hex daily HMAC pseudonym. BFF/API body binding is rawBody + newline + guestToken (empty when absent). API rejects non-pseudonymous network values. The capability itself is sent in the private service header, never in envelope payload/logs. Treat envelopes as credentials and never log them.

Secret scope: API needs SESSION_SECRET/BFF_SERVICE_SECRET; BFF needs BFF_SERVICE_SECRET/NETWORK_HMAC_SECRET/EDGE_SERVICE_SECRET; bridge needs EDGE_SERVICE_SECRET. Worker configuration is isolated to environment/store/database and requires no signing/session keys. Do not provision unused secrets merely because applications share a config package.
