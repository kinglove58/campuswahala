# ADR 014: Campus life on the academic timeline

Status: Phase 4 implementation for review. Base `f3edf1b5ca7ac598eb73d683339f88e30c71fb64`. No Phase 5, deployment or automatic merge.

AcademicTerm.minute is the only advancing game clock. LifeSimulation.lastProcessedMinute is a processing watermark, never an independent clock. START_TERM attaches a versioned LifePolicy snapshot and a valid virtual hostel home in the same transaction; existing pre-Phase-4 active terms use explicit START_LIFE. GET never initializes, decays, triggers or resolves state. Starting the next term resets the watermark to that term's initial minute while retaining metrics/fractional remainders/story flags; there is no intersemester or real-wall-clock decay.

AcademicService and LifeService enter the same User-first locking helper, revalidate the account session/status inside the lock, then read/write academic, life, occurrence and receipt state. All time-advancing academic commands process life before commit. Life actions call the existing academic processTime, update the active academic snapshot/revision and life snapshot in that same transaction. A receipt/capacity/error failure rolls everything back. No service opens a nested transaction and no worker requires new credentials. Completed academic results and grade policy stay immutable: life changes time allocation, never scores, mastery, GPA or progression.

Four integer metrics (energy/satiety/mood/wellbeing) are bounded 0–10000 in strict domain parsing and PostgreSQL CHECK constraints. A minute-based integer accumulator carries fractional decay and preserves low-satiety threshold effects across equivalent batches; interval replay is a no-op. The supported four-week semester spans 40,320 elapsed minutes; its absolute end minute is 40,740 because Phase 3 begins at minute 420 (07:00). Domain/DB watermark bounds include that offset. Policy v1 owns starting values, decay, extra hungry mood decay, travel energy cost, meals/rest/sleep/social/exercise effects, permitted venues/durations and event budgets. No optional exhaustion lockout is enabled in v1: travel, exams and recovery remain available at zero. Recovery is clamped, with no death/game over, diagnosis, medical advice, nutrition/calories, real residence or real GPS.

The private aggregate uses a bounded JSON snapshot, not one table per activity. Separate WahalaOccurrence records retain a selected versioned template, bounded virtual context, server roll, choice and applied effects. DB uniqueness permits only one pending event per owner; finalized outcomes reject rewrites. A bounded 60-occurrence lookup covers at most 40 events in the current term plus recent cross-term context. Historical occurrences persist for audit; recent-story presentation shows eight. With the existing 100-term academic cap, v1 occurrence history is bounded to 4,000. Prior terms' pending situations expire on term attachment.

Ten fictional templates use strict non-executable eligibility operators. No eval/JavaScript, sensitive identity traits, real location, external account data or client preview weather enters context. Trigger checkpoints require meaningful authoritative time advancement, never frames/GET/cosmetic coordinates. Server crypto selection records its roll and eligible IDs; the pure selector accepts injected test RNG. Selection is limited to one pending situation, 180 minutes globally, at least 1,440 minutes per template, two per game day and 40 per term. Effects are time/four metrics/allowlisted story flags only. Every template has a zero-time neutral route. Pending events do not block academics; they expire naturally. Location-bound meaningful choices revalidate campus/venue conditions; neutral dismissal remains possible elsewhere.

Life commands are a strict UUID-keyed private union. Owner derives exclusively from the HttpOnly principal. Same parsed command hash/key returns the original compact acknowledgement plus current private view; differing content conflicts. Life receipts have a ≤2 KB acknowledgement and a 2,000-per-term capacity. No key is evicted; capacity rejects transactionally. User/character deletion cascades life state and User deletion cascades occurrences/receipts. Existing revocation and SKIP LOCKED worker behavior is unchanged.

Private BFF/API life routes bind account/body/session under the existing signed context and replay protection, client/network quotas and shared account limit. All responses are no-store. SW caching remains an explicit static/public allowlist; life/academic/private routes are excluded. Browser metrics/buttons are presentation only. Offline life commands are refused; one uncertain command is retained only in memory, with explicit same-ID retry after reconnect. No background sync or automatic mutation replay.

CW Pocket and actual venue panels expose server-derived actions. On initial simulated waking and successful sleep acknowledgement, presentation resumes at a validated manifest home spawn and saves only the cosmetic safe return. The same helper cannot change server time/presence. A visual venue mismatch hides activities until authoritative travel; the API independently validates venue/time/option/occurrence. Meals are fictional simulation choices, never real vendor menus. Socialize is solo ambience, not chat/multiplayer. No money, economy, XP, valuable inventory, ads or Phase 5 social systems are introduced.

Private academic/life hooks coalesce in-flight reads. Account-world/academic/life GETs retry HTTP 429 only within a 75-second/15-attempt bound, with no-store, abort on unmount and no storage. Life refreshes on academic revision, focus/reconnect and explicit refresh rather than a competing periodic poll. This respects unchanged quotas while allowing a busy campus to reopen after a rate window. Mutation retries remain explicit and retain the same UUID, including a known rate refusal; there is no automatic mutation replay.
